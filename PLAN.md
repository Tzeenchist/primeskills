# primeskills — план

Замена gstack: тот же цикл разработки, но без раздувания контекста, без телеметрии,
с явными правилами поведения агента. Документ фиксирует замысел до реализации.

---

## 1. Зачем

### Измеренная причина

Объём текста, который gstack вливает в контекст на одном проходе пайплайна
(только `SKILL.md` + секции, без файлов проекта):

| скилл | слов |
|---|---|
| review | 18 720 |
| office-hours | 14 020 |
| autoplan | 13 812 |
| plan-ceo-review | 12 846 |
| qa | 12 376 |
| plan-design-review | 12 331 |
| ship | 11 856 |
| plan-eng-review | 9 660 |

Полный проход **office-hours → ceo → eng/design → реализация → qa → review → ship**
это ≈ 92 000 слов инструкций ≈ **130–150k токенов** до того, как агент прочитал
хоть одну строку кода. Отсюда и 70% пятичасового лимита.

Для сравнения, `obra/superpowers`: самый большой скилл — 4 823 слова, медиана ≈ 1 000.
`andrej-karpathy-skills` — 371 слово на весь набор. То есть десятикратное сжатие
достижимо, это не гипотеза.

### Цели

1. Полный цикл разработки укладывается в **< 15k токенов** инструкций.
2. Ноль телеметрии, ноль сетевых вызовов «домой», ноль сбора статистики.
3. Только необходимая философия — принципы, меняющие решение агента, а не эссе.
4. Поведение агента ограничено явно (что читать, что править, когда останавливаться).
5. Работает в Claude Code, Codex, Kimi Code, OpenCode, Agy.

### Анти-цели

- Не переносить gstack целиком «в сжатом виде» — это будет тот же gstack.
- Не строить фреймворк с плагинами, реестрами и рантаймом. Скиллы — это markdown.
- Не делать Mem0 обязательным.

## 2. Архитектура: три уровня загрузки

Главный приём — **прогрессивное раскрытие**. Агент грузит не скилл целиком,
а ровно тот слой, который нужен на текущем шаге.

```
core/PRINCIPLES.md      ~400 слов   грузится всегда, один раз за сессию
skills/<name>/SKILL.md  ~600 слов   грузится при вызове скилла
skills/<name>/ref/*.md  без лимита  грузится по явной ссылке из SKILL.md, если понадобилось
```

Правило бюджета: `SKILL.md` **не длиннее 800 слов**. Всё, что не влезло — чеклист,
таблица, шаблон отчёта — уезжает в `ref/` и читается только когда доходит очередь.
Линтер в CI режет PR, если бюджет превышен.

Второй приём — **вычитание из общего**. Всё, что повторяется в каждом скилле
gstack (преамбулы, дисклеймеры, описание ролей, формат вывода), выносится в
`core/` один раз.

## 3. Пайплайн и состав

Привычная последовательность сохранена, изменился вес шагов и имена
(имена разведены с gstack, см. BUILD-PLAN §1).

```
brief*  →  plan  →  ceo | eng | beauty      (порядок линз по задаче)
                       ↓
                     build  ⇄  verify  ⇄  debug
                       ↓
                 vet  ·  probe
                       ↓
                     land

* опционально, не всегда
handoff — в любой момент: передать работу следующей сессии или агенту
baby    — в любой момент: объяснить предыдущий вывод
```

### Пятнадцать скиллов

|---|---|---|---|
| `brief` | read-only | 800 | разведка намерения, урезание скоупа |
| `plan` | read-only | 600 | план с критериями приёмки |
| `ceo` | read-only | 300 | линза: та ли задача |
| `eng` | read-only | 300 | линза: архитектура, краевые случаи |
| `beauty` | read-only | 300 | линза: иерархия, состояния, доступность |
| `build` | write | 700 | реализация, цикл TDD |
| `debug` | write | 600 | отладка от воспроизводимого бейзлайна |
| `verify` | write | 400 | доказательство «сделано» |
| `probe` | read-only | 800 | поведение работающей системы |

Тонкие оркестраторы: знают имена и порядок, но не содержание (BUILD-PLAN §8).

### Арифметика бюджета

| | слов |
|---|---|
| 15 скиллов | 7 800 |
| 4 потока | 570 |
| `core/` — всегда загружаемая часть | 1 367 |

## 4. Фундаментальные принципы

Пять принципов инженерного мышления. Каждый живёт **в одном месте** — либо в
`core/PRINCIPLES.md` (если влияет на каждое действие), либо внутри профильного
скилла (если срабатывает только там). Дублирование запрещено — это и есть
главный источник раздувания в gstack.

| принцип | суть | откуда | где живёт |
|---|---|---|---|
| **Безжалостное урезание скоупа** (YAGNI & Cut Scope) | Искать, что выбросить из задачи без потери ценности; строить минимальный жизнеспособный вариант | gstack `office-hours`, superpowers `brainstorming` | `office-hours` + `plan-ceo-review` |
| **Первые начала, нулевые абстракции** | Нативные возможности языка (30–50 строк понятного кода) вместо сторонних библиотек и паттернов | karpathy-skills | `core/PRINCIPLES.md` |
| **Научная отладка от воспроизводимого бейзлайна** | Не угадывать причину и не сыпать случайные патчи: изолировать минимальный падающий пример, выдвинуть гипотезу, проверить типы данных | karpathy-skills, superpowers `systematic-debugging` | `debug` |
| **Полнота состояний интерфейса + производительность** | Проектировать UI не только для идеального сценария, но и для краевых случаев, с контролем отклика и доступности | addyosmani, gstack `design-review` | `plan-design-review` + `qa` |
| **Поиск корня проблемы** (Root-Cause Invariants) | Чинить первопричину в источнике данных, а не маскировать симптом через `?.` и пустые `try/catch` | Aider, superpowers | `core/PRINCIPLES.md` |

Два из пяти — сквозные (нулевые абстракции, корень проблемы), их агент должен
держать в голове всегда. Остальные три включаются вместе со своим скиллом.

## 5. Жёсткие правила (Agent Guardrails)

| правило | формулировка | откуда | как обеспечивается |
|---|---|---|---|
| **Ограничение радиуса изменений** | Править только запрошенные строки. Запрет на попутный рефакторинг, переформатирование соседних функций, удаление комментариев вне скоупа | Aider, superpowers | `core/GUARDRAILS.md` + проверка в `review` |
| **Жёсткий гейт планирования** | Не писать и не менять код, пока пользователь явно не подтвердил план и критерии приёмки | superpowers `writing-plans`, gstack `plan-eng-review` | `flow/plan` завершается остановкой; скиллы планирования без права записи |
| **Ограничение чтения контекста** | Не читать файлы целиком (особенно > 200 строк). Точечный поиск `rg`/`grep`, просмотр сигнатур, чтение фрагментов через `offset/limit` | SWE-agent (ACI) | `core/GUARDRAILS.md`; в стеке есть `codegraph` — предпочитать его grep-циклу |
| **Детерминированная верификация** | Код не работает, пока не запущены тесты/линтеры. Валидация строго по коду возврата (`exit 0`) и логу раннера (`0 failed`), а не по отсутствию краша | anthropic-quickstarts, superpowers `verification-before-completion` | `verify` — обязательный шаг перед `ship` |
| **Матрица 5 состояний UI + a11y** | Для любого интерфейсного компонента явно обработаны `Loading`, `Empty`, `Error`, `Partial/Initial`, `Success`; проверена навигация `Tab`/`Enter`/`Esc` | addyosmani, gstack | чеклист в `plan-design-review/ref/` и `qa/ref/` |
| **Двухпроходный аудит коммита и секретов** | Перед коммитом `git diff --staged`: (1) нет ключей, токенов, паролей, изменений `.env`; (2) текст сообщения совпадает с реальными строками диффа (Conventional Commits) | Aider, cline, litellm | `ship`, шаг pre-commit |
| **Ролевая изоляция прав** | В аналитических скиллах (`plan-ceo-review`, `plan-eng-review`, `plan-design-review`) запрещены инструменты изменения файлов — только чтение, анализ, вывод плана | cline (режимная модель) | `allowed-tools` во frontmatter + текстовый запрет в теле |


### 5а. Гигиена харнесса и окружения

| правило | формулировка | есть в источниках? |
|---|---|---|
| **Детерминированная песочница** | Тесты — в изолированном окружении, с фиксированными сидами и замоканными внешними API. Никогда не менять живые БД и не дёргать продовые эндпоинты | частично: `addy/test-driven-development` говорит про детерминизм как про качество теста, про изоляцию окружения — нигде |
| **Неприкосновенность харнесса** | Никогда не править фикстуры, пороги и наборы проверок ради зелёной сборки. Чинить код приложения | **нигде.** Единственное совпадение по гребу — про временное снижение порога алерта, к теме не относится |
| **Уборка за собой** | Всегда гасить порождённые фоновые процессы и удалять временные артефакты тестов | **нигде** (только косвенные упоминания) |

### 5б. Циклы исполнения и предохранители

| правило | формулировка | есть в источниках? |
|---|---|---|
| **Предохранитель** | Максимум 3 неудачные попытки на одном баге или тесте. Застряли — откат (`git checkout`) и вопрос пользователю | **нигде как механизм.** Дух есть: superpowers запрещает «повторный прогон той же модели без изменений», у TDD есть раздел When Stuck. Числа и отката нет |
| **Строгий цикл TDD** | Red (падающий тест) → Green (минимальный проходящий код) → Refactor (уборка). Фазы не смешивать | есть: superpowers `test-driven-development`, `verification-before-completion` |
| **Никаких слепых повторов** | Каждая повторная попытка проверяет принципиально новую гипотезу, а не косметику | есть по смыслу: `systematic-debugging`, правило одной гипотезы против «дробовика» |
| **Проверка на регресс** | Цикл закрыт, только когда прошёл и новый тест, и полный набор тестов | частично: `finishing-a-development-branch` гоняет полный набор, но связка «и то, и другое» не сформулирована |

Итог проверки: из семи правил **четыре не имеют прототипа** в пяти источниках
(неприкосновенность харнесса, уборка, предохранитель с числом и откатом,
изоляция окружения). Три остальных есть, но разрозненно.

Размещение: гигиена харнесса и предохранитель — в `core/GUARDRAILS.md`
(действуют всегда); цикл TDD — в `build`; проверка на регресс — в `verify`.

### 5в. Терминальная безопасность

| правило | формулировка |
|---|---|
| **Чёрный список деструктивных команд** | Жёсткий запрет: `rm -rf` без точного пути, `git reset --hard` (без предварительной бэкап-ветки), `git push --force`, `DROP DATABASE`/`DROP TABLE`/`TRUNCATE`, `killall`, `kubectl delete`, `docker system prune` |
| **Права на историю git** | Агент может только: создавать ветки, коммитить, читать `diff`/`log`. Переписывание истории, force-push и сброс — вне его полномочий |

**Что нашлось в источниках.** Это единственное место, где у gstack есть не текст,
а **работающий механизм**: скилл `careful` (400 слов) ставит `PreToolUse`-хук на
`Bash`, матчит команду по списку паттернов и возвращает `permissionDecision: "ask"`.
Скилл `freeze` тем же способом блокирует `Edit`/`Write` вне заданной директории.
Оттуда же берём готовый список безопасных исключений
(`rm -rf node_modules`, `dist`, `__pycache__`, `.cache`, `coverage`).

Забираем механику целиком, **вырезав телеметрию**: в теле `careful` зашит
`echo … >> ~/.gstack/analytics/skill-usage.jsonl` на каждый вызов. Ровно тот сбор,
от которого уходим.

`freeze` попутно закрывает два открытых вопроса: он и есть техническое
обеспечение «ограничения радиуса изменений», и он же — способ реализовать
ролевую изоляцию в Claude Code. Для Codex/Kimi/OpenCode хуков нет, там остаётся
текстовый запрет.

У superpowers по теме — только формулировки («Never `--force` on your own
initiative»), без механизма. Полезны их таблицы самооправданий: «пуш отклонили,
force-push починит» — с разбором, почему это ложь.

### 5г. Чекпоинты и бюджет контекста

| правило | формулировка |
|---|---|
| **Чекпоинт каждые 2–3 шага** | После каждых 2–3 выполненных шагов плана — фиксация статуса в `TODOS.md`/`PLAN.md` и атомарный коммит |
| **Безопасный перезапуск** | Перегруженную сессию можно оборвать и продолжить с последнего отмеченного шага в файле, не теряя нити |

Причина — деградация на длинной сессии: контекст забивается логами, и качество
решений падает раньше, чем кончается окно.

**В источниках** ближе всех `superpowers/subagent-driven-development`: там прямо
сказано, что память разговора не переживает уплотнение контекста, и вводится
**ledger** — файл, который переживает. Механика годная, но она стоит 4 823 слова
и завязана на исполнение субагентами. Берём идею, отбрасываем обвязку: одна
таблица статусов в файле репозитория плюс правило коммита.

Важно, что чекпоинт — это **файл в репозитории, а не память агента**. Тем он и
ценен: его видно человеку и он переживает `/clear`.

### 5г-бис. Защита от протаскивания по инерции (G16)

| правило | формулировка |
|---|---|
| **Перенесённое — сверить или снять** | Всякое утверждение, перенесённое из прошлого шага (открытый вопрос, остаток работы, замечание, статус), при повторении сверяется с текущей записью или не повторяется |
| **Якорь** | У открытого пункта есть адрес: файл и строка, коммит, задача или сообщение, которым он поднят. Нет якоря — это воспоминание, снять |
| **Запись бьёт память** | Чекпоинт говорит «открыто», запись говорит «решено» — верна запись |
| **Закрытое помечается, а не стирается** | У решённого остаётся строка с решением, чтобы повторное поднятие противоречило написанному |

Развёрнуто в BUILD-PLAN §16. Прототипа нет ни в одном источнике.

### 5г-трис. Разрешение цели перед разрушением (G17)

Из инцидента snirrex-pro 2026-05-30: прогон тестов снёс dev-БД, потому что в
`settings/test.py` имя тестовой базы совпадало с боевым. Агент выполнил
`manage.py test` — команду, которой нет ни в одном чёрном списке.

| правило | формулировка |
|---|---|
| **Разрешить цель до запуска** | Перед тестами, миграциями, загрузкой фикстур — напечатать фактическое имя базы/схемы/каталога и сверить с ожидаемым. Проверяется разрешённое имя, а не текст команды |
| **Рабочая и dev-база — не тестовые** | Тесты только на изолированной `test_*` |
| **Отсутствие гейта — не разрешение** | В режимах `danger-full-access` / `skip-permissions` / `yolo` деструктивная операция с данными всё равно требует подтверждения пользователя |
| **Не обходить чужой guard** | Проверка, поставленная после инцидента, — часть харнесса (**G8**) |
| **Бэкап до, не после** | Для кода `git stash create` (**G14**), для данных — дамп |

Развёрнуто в BUILD-PLAN §18. Чёрный список команд (**G10**) этот случай
не ловит — в этом и смысл отдельного правила.

### 5д. Эскалация на человека

Список ситуаций, где агенту запрещено решать самому:

- **Противоречие в бизнес-логике** — два требования исключают друг друга.
- **Изменение публичных контрактов API**, затрагивающее сторонние сервисы.
- **Появление платных внешних зависимостей** или смена лицензии.
- Плюс из раздела 5б: **три неудачные попытки** на одном месте.
- Плюс из раздела 5в: любая команда из чёрного списка.

**В источниках** каркас есть у superpowers — «четыре вещи останавливают тебя,
и только они» в `subagent-driven-development`, и разбор самооправданий
(«они наверняка хотят, чтобы я смержил») в `finishing-a-development-branch`.
Форма хорошая: закрытый список плюс таблица отговорок. Содержание берём ваше —
про лицензии и платные зависимости не пишет никто.

Ключевое в формулировке — **закрытость списка в обе стороны**: перечисленное
эскалируется всегда, неперечисленное агент решает сам. Открытый список
(«эскалируй, когда сомневаешься») на практике означает либо паралич, либо
свободу трактовки.

## 6. Поддержка агентов

Первый этап: **Claude Code, Codex, Kimi Code, OpenCode**. (Agy отложен.)

Проблема: единого формата скиллов нет. Claude Code читает `SKILL.md` с YAML
frontmatter и уважает `allowed-tools`. Codex и OpenCode читают `AGENTS.md`
и свои конфиги, `allowed-tools` не понимают.

Решение — **один источник, генерируемые адаптеры**:

```
skills/<name>/SKILL.md          ← канон, пишем только его
adapters/claude/                → симлинки в ~/.claude/skills/
adapters/codex/AGENTS.md        → сборка индекса скиллов
adapters/opencode/opencode.json → регистрация команд
adapters/kimi/
```

`bin/primeskills install <agent>` раскладывает адаптеры. Ролевая изоляция там,
где `allowed-tools` не поддерживается, деградирует до текстового запрета в
первых строках скилла — слабее, но не ноль.

## 7. Mem0 — опция, не правило

В стеке уже развёрнут mem0 (Postgres `mem0_memory`, свой MCP-сервер во всех
агентах, четыре провайдера на переключателе). Встраиваем так:

- По умолчанию **выключено**. Скиллы работают без единого обращения к памяти.
- Включается флагом `PRIMESKILLS_MEM0=1`.
- **Чтение**: `plan-*` поднимает прошлые решения по проекту.
- **Запись (auto-sync)**: перед закрытием цикла `ship` обязан записать в память
  то, что не выводится из кода и истории git: неочевидное архитектурное решение
  и его причину, редкий баг с симптомом и корнем, отвергнутый вариант с
  обоснованием. Вызов `add_memory(fact=…, project_id=…)`.
- **Что не писать**: то, что и так есть в коде, в `git log` или в `PLAN.md`.
  Без этого фильтра память заполняется пересказом диффов и перестаёт работать.
- Без правила записи агент отлично читает память и никогда её не пополняет —
  это самый частый способ похоронить такую систему.
- Отсутствие mem0 никогда не ломает скилл — деградация тихая.

## 8. Язык

- **Вывод — на языке ввода.** Спросили по-русски → отвечаем по-русски.
- **Размышление — на любом**, русском или английском, что эффективнее для модели.
- Сами скиллы пишем по-английски (модели лучше следуют англоязычным инструкциям),
  а в `core/` кладём одну строку про язык вывода.

## 9. Решения по спорным местам

Обсуждено, зафиксировано:

| вопрос | решение |
|---|---|
| Чтение контекста | **Бюджет, не запрет.** Файл целиком читать можно, если он короче ~200 строк или это явно дешевле точечного поиска. Лимит — на задачу, не на вызов. |
| Гейт планирования | **По радиусу изменений.** Правка в одном файле без смены контракта — без гейта. Новый модуль, миграция, публичный API — гейт обязателен. |
| `office-hours` | **Переделываем синтезом** с `superpowers/brainstorming` как скелетом. Не переносим ритуал, берём давление на скоуп. Кластер 1 карты синтеза. |
| `review` / `qa` | **Разводим жёстко.** `qa` — поведение работающей системы. `review` — свойства диффа. Общий чеклист один, в `core/`. |
| Матрица 5 состояний UI | **Открыто.** Предварительно в `ref/` скилла `ui`, чтобы не грузилась на бэкенд-задачах. Вернёмся, когда дойдём до скилла. |
| Agy | **Вычеркнут** на первом этапе. Агенты: Claude Code, Codex, Kimi Code, OpenCode. |
| Ролевая изоляция вне Claude Code | Открыто: текст в промпте или hook-обёртка. Решаем при написании адаптеров. |
