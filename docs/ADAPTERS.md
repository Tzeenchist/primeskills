# Установка и ролевая изоляция

## Один источник правды

`bin/primeskills-install` связывает каталог `skills/` с каждым агентом. Ничего
не копируется — правка `SKILL.md` в репозитории действует во всех агентах сразу.

```
python3 bin/primeskills-install            # печатает план, ничего не меняет
python3 bin/primeskills-install --apply     # связывает
python3 bin/primeskills-install --uninstall --apply
python3 bin/primeskills-install claude --apply   # только один агент
```

| агент | куда | как |
|---|---|---|
| Claude Code | `~/.claude/skills/<имя>/` | настоящий каталог, файлы внутри — симлинки (так же ставится gstack; иначе `ref/` не виден) |
| Codex | `~/.codex/skills/<имя>` | симлинк на каталог |
| OpenCode | `~/.config/opencode/skills/<имя>` | симлинк на каталог |
| Kimi | `extra_skill_dirs` в `~/.kimi-code/config.toml` | симлинки не нужны, достаточно пути |
| Oh My Pi (`omp`) | `$PI_CODING_AGENT_DIR/skills/<имя>` или `~/.omp/agent/skills/<имя>` | симлинк на каталог; core в `AGENTS.md` того же agent dir |
| Qoder | `~/.qoder/skills/<имя>` | симлинк на каталог; core в `~/.qoder/AGENTS.md`, команды в `~/.qoder/commands/`, сторож в `~/.qoder/settings.json` |

### Откуда каждый хост берёт скиллы

Записано 2026-08-18 по документации Kimi, а не по догадкам: у Kimi **пять**
источников, и `extra_skill_dirs` — только один из них.

| источник | что там сейчас |
|---|---|
| `~/.kimi-code/skills/` | каталога нет |
| `~/.agents/skills/` | `find-skills`, `modern-web-guidance` |
| `.kimi-code/skills/` в корне проекта | нигде не заведён |
| `.agents/skills/` в корне проекта | нигде не заведён |
| `extra_skill_dirs` в `config.toml` | **наш `skills/`** |

Приоритет: проект > пользователь > extra > встроенные. Отключить конкретный
пользовательский каталог конфигом нельзя — только убрать из него содержимое.

**gstack доходил до Kimi через `~/.agents/skills`** — межагентный каталог, на
который не ссылается ни один конфиг. 2026-08-17 его содержимое (111 записей)
перенесено в `~/.agents/skills_archive`, и с тех пор Kimi gstack не видит.
2026-09-02 архив перенесён дальше, в `~/.gstack/skills_archive` (вместе с
`skills.backup-20260331` → `~/.gstack/skills.backup-20260331`): freebuff CLI
импортирует все `*.ts` из подкаталогов `~/.agents` как локальных агентов
Codebuff и падает на чужих скриптах с side effects
(`gstack/design/prototype.ts` делает `process.exit(1)` без `OPENAI_API_KEY`).
Проверено не конфигом, а самим Kimi: `kimi -p` со списком доступных скиллов
печатает 27 наших, два из `~/.agents/skills` и три встроенных, ни одного
gstack. Конфиг говорит, что подключено; вопрос «что видит агент» отвечает
только агент.

**Коллизии.** Установщик проверяет, занято ли имя чужим скиллом, и только тогда
добавляет префикс `prime-`. Сейчас коллизия ровно одна: `autoplan` у gstack в
`~/.claude/skills`, поэтому наш встал как `prime-autoplan`. Удаление снимает
только те записи, что ведут в этот репозиторий, — чужое не трогается.

### Как позвать хост живьём

Записано 2026-09-23 по двенадцати живым вызовам гейта выпуска (PS-088: `screen`
и `probe` против шести хостов). Ни одна строка здесь не выведена из
документации — каждая получена запуском, и половина далась не с первого раза.

| хост | команда, которая работает |
|---|---|
| claude | `claude -p "<промпт>"` |
| codex | `cd <репозиторий> && codex exec --skip-git-repo-check -c 'sandbox_mode="danger-full-access"' "<промпт>" < /dev/null` |
| kimi | `kimi -p "<промпт>"` — **мёртв по подписке**, см. ниже |
| opencode | `opencode run --model zai-coding-plan/glm-5.3-flash "<промпт>" < /dev/null` |
| omp | `omp -p --model tencent/hy3 "<промпт>" < /dev/null` |
| qoder | `qodercli -p "<промпт>"` |

**Сначала установка, потом вызов.** Хосты читают закреплённую копию, и нового
скилла в ней нет: пока не сделан `primeskills-install --live --apply` (или
перепин на версию с этим скиллом), агент отвечает «неизвестный скилл». Гейт
живых вызовов требует звать то, чего хост ещё не видит, — эту петлю разрывает
только установка из рабочего дерева.

**Четыре грабли, по одной на хост.**

- **codex** без `< /dev/null` печатает `Reading additional input from stdin...`
  и висит до таймаута, а запущенный вне доверенного каталога отвечает
  `Not inside a trusted directory and --skip-git-repo-check was not specified`.
  Нужны обе поправки сразу: запуск из репозитория и закрытый вход.
- **omp** без `-p` ждёт вход из трубы, а с закрытым входом умирает по SIGHUP
  (код 129): это TUI, которому нужен терминал. Модель по умолчанию отвечает
  `404 This model is unavailable for free` и сама называет замену —
  `tencent/hy3`.
- **opencode** с открытым входом даёт ноль байт до таймаута — то самое
  поведение, что записано про него с 2026-09-08. С `< /dev/null` и явной
  моделью отвечает и **действительно вызывает скилл**: в выводе видно
  `Skill "screen"`.
- **claude** в неинтерактивном режиме отказывает собственному инструменту
  Skill («Execute skill: screen») и читает `SKILL.md` файлом. Ответ верный, но
  это чтение, а не вызов, — при записи `note livecall` разницу называть.

**kimi недоступен с 2026-09-23:** `kimi -p` отвечает
`403 provider.auth_error: Your current subscription does not have access to
Kimi Code`. Три захода с разными гипотезами (вход, терминал, модель) ничего не
меняют — причина на стороне аккаунта, и до восстановления подписки пары
`<навык>×kimi` закрыть нечем.

### Меню `/` у OpenCode и Kilo

Скиллы и команды у этих хостов — два разных списка, и меню дополняет только из
второго. Скиллы уезжают модели блоком `<available_skills>`; загрузчик команд
сканирует `{command,commands}/**/*.md`, и `/` подсказывает из него. Связанных
скиллов для подсказки недостаточно: имя приходится набирать целиком.

Поэтому установщик пишет на каждый навык файл-обёртку —
`~/.config/opencode/command/<имя>.md` и `~/.config/kilo/command/<имя>.md`. Внутри
описание из `SKILL.md` (его и показывает меню) и тело в одну строку: взять навык
`<имя>`, аргументы через `$ARGUMENTS`. Инструкции остаются в `SKILL.md` —
файл команды ярлык, а не вторая копия.

Своё от чужого отличается строкой `<!-- primeskills:command -->` внутри файла:
команда — обычный markdown в каталоге, куда пишет и сам пользователь, так что
владение читается из файла, а не угадывается по пути. Файл без маркера не
перезаписывается и не удаляется, о нём сказано в отчёте строкой `LEFT ALONE`.
Команда навыка, выбывшего из набора, снимается при следующей установке.

**Проверено вживую 2026-09-19**, на временном `HOME`: `opencode serve` и
`GET /api/command` вернули 33 команды — 31 наша плюс встроенные `init` и
`review`, — и у `/eng` описание из `skills/eng/SKILL.md`. Тот же ответ у
`kilo serve`. Версии: opencode 1.18.31, kilo 7.4.23. Формат взят из встроенной
документации самого хоста (`## Commands` в бинарнике), а не из догадки.

### Qoder

Записано 2026-09-21 по самому бинарю `qodercli` 1.1.60 и живому вызову, а не по
сходству имён. Поверхность повторяет Claude Code: каталог конфига —
`~/.qoder` (переносится флагом `--config-dir`), внутри `skills/`, `commands/`,
`agents/` и `AGENTS.md`, который хост читает в каждой сессии с областью `home`.
Хуки — `hooks.PreToolUse[].matcher` в `settings.json`, тот же формат, что у
Claude Code, поэтому сторож `fence` здесь настоящий, а не текст. Какие команды
взвёл установщик, записано в `~/.primeskills/hooks.json`: владение хуком решает
запись, а не путь, иначе прогон из другого дерева набора считает чужим то, что
написал сам набор (PS-087). Команды меню
берут `$ARGUMENTS` и описание из фронтматтера — обёртки те же, что у OpenCode,
только каталог называется `commands` во множественном числе.

**Форма установки — симлинк на каталог.** Исключение Claude Code, где груз
`ref/` не виден через ссылку на каталог, здесь не действует: живой вызов
2026-09-21 прочитал `ref/security.md` внутри навыка, поставленного одной
ссылкой. Условие у этого одно — цель ссылки должна лежать внутри доверенного
каталога хоста (`permissions.trustDirectories` в `settings.json`, на этой
машине `/home/admin`). Установщик линкует из `~/.primeskills/pinned`, то есть
условие выполняется само; закреплённое дерево за пределами доверенных
каталогов сделало бы `SKILL.md` читаемым, а его `ref/` — нет.

`~/.agents` qoder тоже знает, но только как «legacy .agents/skills
compatibility directory» — для навыков, не для `AGENTS.md`. Блок core приезжает
один раз, из `~/.qoder/AGENTS.md`; общий файл cline при этом не трогается.

**Профиль `prime-analyst` здесь не ставится.** Каталог `~/.qoder/agents` хост
сканирует, но во фронтматтере определения агента разбираются `name`,
`description`, `whenToUse`, `model`, `color` и `disable-model-invocation` —
списка инструментов среди них не нашлось. Профиль без отбора инструментов был
бы украшением, а не ролевой изоляцией, поэтому его нет, как нет его у Claude
Code, Codex и OMP. Появится — когда формат будет прочитан в документации
самого qoder, а не выведен из имён ключей.

## Ролевая изоляция: что проверено, а что нет

Двенадцать аналитических скиллов (`brief`, `plan`, `ceo`, `money`, `eng`,
`beauty`, `teams`, `autoplan`, `vet`, `baby`, `measure`, `study`) не должны иметь
возможности писать. `probe` в этом списке стоял ошибочно: его роль —
`exercises`, он гоняет запущенное приложение и пишет его данные, а на хосте,
который профиль соблюдает, оставался без оболочки и не мог выполнить
собственную процедуру. Исправлено 2026-08-19 по разбору Codex.

### Что из этого — гарантия, а что пожелание

Ни одна строка ниже не проверена состязательным тестом, поэтому «enforced»
означает «хост объявляет, что запрещает», а не «мы доказали, что обойти нельзя».

| гарантия | Claude Code | Codex | OpenCode | Kimi | OMP |
|---|---|---|---|---|---|
| `Edit`/`Write` запрещены у read-only | объявлено | объявлено, песочница здесь не работает | объявлено | объявлено | нет смены прав на вызов скилла |
| запись через шелл запрещена | **нет** | нет | **нет** | нет | нет |
| выход за границу каталога запрещён | **нет**: хук видит только `Edit`/`Write`/`NotebookEdit` | нет | нет | нет | нет |
| сетевой доступ ограничен | нет | нет | нет | нет | нет |

Итог одной строкой: **ролевая изоляция у нас — намерение, а не граница
безопасности.** Единственный канал, который действительно перехватывается, —
редакторские инструменты у Claude Code. Всё остальное держится на том, что
модель читает инструкцию и следует ей.

`fence` — предупреждающий слой, а не ограждение: список опасных команд это
список, и шелл денилистом не закрывается. Настоящая граница требует песочницы,
разрешённого рабочего каталога и allowlist инструментов — этого у нас нет.

### Потолок принуждения

Записано 2026-08-18, после того как три внешних разбора сошлись в одном:
сильные принципы, слабое принуждение. OpenCode — «дефицитный ресурс не
контекст, а послушание»; Kimi — дельта над базовой моделью мала; Codex —
8/10 как набор привычек, 4/10 как слой безопасности. Прогон 6 показал это
фактом: `build` был вызван, его красная фаза проигнорирована.

Инструментов принуждения у нас ровно два, и оба дырявые по устройству:

- **хуки** — сильные, но двусредовые (Claude Code и Qoder, 2026-09-22) и видят
  только `Edit`/`Write`/`NotebookEdit`; `sed -i` из `Bash` проходит мимо;
- **запись прогона** (`primeskills-run`) — работает у всех агентов, потому что
  это не перехват, а условие плюс проверяемое состояние; обходится тем, что
  агент просто не вызовет `run`.

Отсюда вывод, который стоит держать перед глазами, прежде чем строить третий:
**полного принуждения из этой позиции не построить.** Мы не владеем циклом
исполнения — только текстом и вспомогательными программами. Достижимый
максимум: сделать нарушение **видимым постфактум** (`primeskills-adherence`) и
**дорогим** (шаг не засчитывается без записи). Всё, что обещает больше, обещает
чужую власть.

Практическое следствие: машина состояний из разбора Codex и состязательные
тесты изоляции отложены не из лени. Строить принуждение поверх набора, про
который ещё неизвестно, вызывается ли он, — это повторить ошибку «добавить до
замера», на которой уже сгорели шесть стендовых плеч.

### Общее состояние на машину

`~/.primeskills/` — не «наш» каталог, а общий для всех агентов на этой
машине: `installed.json` пишет установщик, `lang` пишет `primeskills-help` из
любой сессии любого агента. Записанное там значение может появиться без ведома
того, кто сейчас работает.

Найдено на живом случае: `lang` со значением `ru` возникло 2026-08-17 в 15:21
и выглядело утечкой из тестов. Изоляция тестов оказалась ни при чём — это
сессия Codex, стартовавшая за шестнадцать секунд до того, выполнила шаг 3
скилла `primeskills`, ровно как там написано. Проверять надо было соседей, а не
тесты.

Состояние прогона (`.primeskills/run/`) устроено иначе — оно лежит в
репозитории, к которому относится, и общим не бывает.

| агент | механизм | статус |
|---|---|---|
| **Claude Code** | `allowed-tools` во frontmatter | **работает.** Поле стоит в самих скиллах, поэтому переживает симлинк и не требует генерации. Линтер сверяет его с `role` (правило F10) |
| **Codex** | профиль `[profiles.prime-analyst]`, вызов `codex -p prime-analyst` | **синтаксис верный, песочница в этой среде не работает** — см. ниже |
| **Kimi** | профиль `~/.kimi-code/agents/prime-analyst.md` | **работает.** Запуск с несуществующим профилем печатает список доступных, и `prime-analyst` в нём есть. `tools` разрешает Read/Grep/Glob, `disallowedTools` запрещает Edit/Write/NotebookEdit |
| **OpenCode** | профиль `~/.config/opencode/agents/prime-analyst.md` | **работает.** `opencode agent list` показывает `prime-analyst (primary)`. `permission: edit: deny, write: deny` |

### Codex: песочница здесь не работает вовсе

Синтаксис профиля подтверждён документацией и совпадает с тем, что у нас
записано: `[profiles.NAME]` с ключами `sandbox_mode`
(`read-only` / `workspace-write` / `danger-full-access`) и `approval_policy`
(`untrusted` / `on-request` / `never`).

Но проверка живьём дала другое. `codex sandbox` с записью файла:

| режим | результат |
|---|---|
| `read-only` | `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`, файл не создан |
| `workspace-write` | **та же ошибка**, файл не создан |
| `danger-full-access` | отработало, файл создан |

То есть `bubblewrap` в этой среде сломан, и падают **оба** ограничивающих
режима, а не только read-only. Файл не появился не потому, что песочница
удержала запись, а потому, что команда вообще не запустилась.

Практический вывод: профиль `prime-analyst` с `sandbox_mode = "read-only"`
здесь «защищает» тем, что не даёт выполнить ничего, включая `git diff`, который
нужен `vet`. Это не изоляция, а неработоспособность. Там, где `bwrap` исправен,
профиль сработает как задумано; здесь для Codex остаётся `approval_policy`
и текстовый запрет.

Раньше в этой таблице стояло «проверено частично: конфиг разбирается, флаг
принимается». Разбор конфига и приём флага не говорят ничего о том, режет ли
песочница запись, — и это ровно та подмена, против которой написан G4.

### Как это нашлось

Четыре попытки угадать формат провалились: файл в `~/.config/opencode/agent/`
(единственное число), ключ `agent` в `opencode.json`, интерактивная
`opencode agent create`, проектный `.opencode/agent/`. Ответ был в
документации: каталог называется **`agents/`**, во множественном числе.
Одна буква.

Урок дороже самой правки: **прежде чем разбирать скомпилированный бинарник,
прочитать документацию.** Копание в `strings` не только не дало ответа, но и
стоило контекста — ровно то, против чего написан наш же G3.

Профили лежат в репозитории (`adapters/opencode/`, `adapters/kimi/`) и
связываются симлинками, как и скиллы: один источник правды.

Там, где механизма нет, остаётся текстовый запрет: у каждого read-only скилла
в инвариантах написано, что он читает и докладывает. Это слабее, и делать вид,
что это то же самое, не нужно.
