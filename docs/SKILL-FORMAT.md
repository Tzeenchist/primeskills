# Формат скилла

Единый контракт. Пишем только `SKILL.md`; всё остальное генерируется.

---

## 1. Что вообще стоит денег

Прежде чем проектировать форму, надо понимать, за что платим. Стоимость скилла
складывается из трёх слоёв, и они очень разные:

| слой | когда грузится | цена |
|---|---|---|
| `description` во frontmatter | **всегда, у всех скиллов сразу** | N скиллов × длина |
| тело `SKILL.md` | при вызове скилла | 1 × бюджет |
| `ref/*.md` | по явному условию внутри тела | 0 или 1 × размер |

Первая строка — самая коварная. Агент держит описания **всех** скиллов в контексте,
чтобы понимать, что вызвать. У addyosmani описания по 300+ символов на 24 скилла —
это несколько тысяч токенов постоянного налога ещё до первого вызова. Отсюда
жёсткое правило: **`description` ≤ 140 символов, формулируется как триггер.**

Это же объясняет, почему у нас 9 скиллов, а не 24. Дробность стоит денег в слое,
который нельзя выгрузить.

## 2. Анатомия `SKILL.md`

```markdown
---
name: verify
description: Use before claiming work complete, fixed, or passing
budget: 400
tier: pipeline
role: write
reads: [core/GUARDRAILS]
refs:
  - path: ref/harness.md
    when: тесты трогают внешние сервисы или БД
---

# Verify

## Триггер
Одна-две строки: по какому событию скилл включается и когда точно не нужен.

## Инварианты
3–5 утверждений, всегда истинных. Декларативно, без шагов.
Всё, что повторяется в двух и более скиллах, здесь не пишется — только ссылка
на `core/`.

## Процедура
Нумерованные шаги. У каждого шага — своя проверка:

1. Действие → **verify:** наблюдаемый признак
2. Действие → **verify:** наблюдаемый признак

## Стоп-условия
Когда прекратить и спросить пользователя. Здесь живёт предохранитель
(3 попытки), здесь же — красные флаги.

## Выход
Точный формат результата: что получает следующий скилл в цепочке.

## Ссылки
`ref/harness.md` — читать только если <условие>.
```

Шесть разделов, ни одного лишнего. Ниже — почему именно эти.

## 3. Почему такая структура

### Инварианты отделены от процедуры

Это главное решение формата, и оно прямо лечит болезнь gstack.

**Инвариант** — декларативен, живёт вечно, повторяется между скиллами
(«чиним корень, а не симптом»). **Процедура** — императивна, уникальна для скилла.

В gstack они перемешаны: каждый скилл заново пересказывает философию своими
словами. Отсюда 12 000 слов там, где процедуры на 500. Разделив их, мы получаем
механическое правило дедупликации: **инвариант, встретившийся дважды, уезжает
в `core/` и заменяется ссылкой.** Без разделения такое правило неприменимо —
непонятно, что с чем сравнивать.

### У каждого шага своя проверка

Формат `действие → verify:` взят у Карпатого (§4 Goal-Driven). Он делает
невозможным самый частый провал агента — «я сделал 1, 2, 3, наверное работает».
Шаг без наблюдаемого признака завершения не проходит линтер.

### Выход — это контракт, а не пожелание

Раздел «Выход» описывает, что именно получает следующий скилл. Благодаря ему
цепочка `flow/` собирается из контрактов, а не из пересказа: `plan` отдаёт
список задач с критериями приёмки → `build` их принимает → `verify` возвращает
статус → `review` берёт дифф и статус.

Это же даёт проверяемость: контракт можно нарушить, а «сделай хорошо» — нельзя.

### У `ref/` есть условие загрузки, а не просто ссылка

Не «см. чеклист», а «читать `ref/ui-states.md`, **если дифф трогает UI**».
Без условия агент читает всё подряд, и `ref/` превращается в тот же монолит,
только в двух файлах. Матрица 5 состояний — ровно этот случай.

### Стоп-условия — раздел, а не примечание

Предохранители («3 неудачи → откат и вопрос») работают, только если у них есть
фиксированное место, куда агент смотрит. В подвале скилла их не читают.

## 4. Frontmatter: что реально работает

Честно о том, кто какое поле читает:

| поле | кто читает |
|---|---|
| `name`, `description` | **все агенты** |
| `allowed-tools` | только Claude Code |
| `budget`, `tier`, `reads`, `refs` | **никто из агентов** — наш линтер и генератор адаптеров |

Последняя строка важна: не надо обманываться богатым frontmatter. Для Codex,
Kimi и OpenCode это просто текст в начале файла. Поэтому ролевая изоляция
(`role: read-only`) обязана **дублироваться первой строкой тела** — там её
модель хотя бы прочитает.

`allowed-tools` не пишем руками: генератор выводит его из `role`.

## 5. Правила бюджета (линтер)

```
description       ≤ 140 символов
SKILL.md          ≤ budget слов (по умолчанию 800)
разделов          ровно 6, в заданном порядке
шаг процедуры     обязан содержать "verify:"
ref без when      ошибка
инвариант-дубль   ошибка (встречается в 2+ скиллах → в core/)
```

Линтер — единственный код в проекте. Всё остальное — markdown.

---

## 6. Язык

Скиллы пишем **по-английски**: модели устойчивее следуют англоязычным
инструкциям, а все источники синтеза англоязычны — перевод добавил бы шум
без выигрыша.

В `core/OUTPUT.md` одна строка: **отвечать на языке пользователя**.
Размышление — на любом.

Этот документ и `PLAN.md` — по-русски, они для нас, а не для модели.

## 7. Пример целиком

Скилл `verify`, как он должен выглядеть (400 слов бюджета, здесь сокращённо):

```markdown
---
name: verify
description: Use before claiming work complete, fixed, or passing
budget: 400
tier: pipeline
role: write
refs:
  - path: ref/harness.md
    when: tests touch external services, databases, or spawn processes
---

# Verify

## Trigger
Before any claim of "done", "fixed", or "passing" — and before commit or PR.
Not needed for read-only analysis.

## Invariants
- Absence of a crash is not a pass. See core/GUARDRAILS § Exit-Code Proof.
- Never edit tests, fixtures, or thresholds to make a build green.
- A cycle closes only when the new test passes AND the full suite passes.

## Procedure
1. Run the project's test command → **verify:** exit code is 0
2. Read the runner summary → **verify:** the line reports 0 failed, 0 errors
3. Run the linter/type-checker → **verify:** exit code is 0
4. Confirm the new test actually fails without the fix → **verify:** revert,
   run, observe red; restore, run, observe green
5. Terminate spawned processes, remove temp artifacts → **verify:** none left

## Stop conditions
- 3 failed attempts on the same failure → roll back, report, ask.
- Tempted to change a test to pass → stop. That is the failure, not the test.

## Output
`PASS` or `FAIL` + command, exit code, failing test names.
```

Обратите внимание: этот скилл содержит **три ваших правила**, которых нет ни
в одном источнике — критерий по коду возврата, неприкосновенность харнесса,
закрытие цикла по полному прогону. При этом он укладывается в 400 слов,
тогда как gstack тратит 30 000 на выпуск и не формулирует ни одного из них.
