# Формат скилла

Единый контракт. Пишем только `SKILL.md`; всё остальное генерируется.

---

## 1. Что вообще стоит денег

Прежде чем проектировать форму, надо понимать, за что платим. Стоимость скилла
складывается из трёх слоёв, и они очень разные:

| слой | когда грузится | цена |
|---|---|---|
| `description` во frontmatter | **всегда, у всех скиллов сразу** | N скиллов × длина |
| указатель на `core/` в файле хоста | **всегда** | 43 слова |
| `core/` целиком | один раз за сессию, по указателю — прогон 5 показал, что до всякого вызова скилла | 1 × 1 760 |
| тело `SKILL.md` | при вызове скилла | 1 × бюджет |
| `calls:` у потока | при вызове потока — тела всех звеньев цепочки | Σ бюджетов |
| `ref/*.md` | по явному условию внутри тела | 0 или 1 × размер |

Первая строка — самая коварная. Агент держит описания **всех** скиллов в контексте,
чтобы понимать, что вызвать. У addyosmani описания по 300+ символов на 24 скилла —
это несколько тысяч токенов постоянного налога ещё до первого вызова. Отсюда
жёсткое правило: **`description` ≤ 140 символов, формулируется как триггер.**

Это же объясняет, почему у нас девятнадцать скиллов, а не втрое больше. Дробность стоит денег в слое,
который нельзя выгрузить.

## 2. Анатомия `SKILL.md`

```markdown
---
name: verify
description: Use before claiming work complete, fixed, or passing
budget: 400
tier: pipeline
role: write
reads: [core/GUARDRAILS]
refs:
  - path: ref/harness.md
    when: тесты трогают внешние сервисы или БД
---

# Verify

## Trigger
Одна-две строки: по какому событию скилл включается и когда точно не нужен.

## Invariants
3–5 утверждений, всегда истинных. Декларативно, без шагов.
Всё, что повторяется в двух и более скиллах, здесь не пишется — только ссылка
на `core/`.

## Procedure
Нумерованные шаги. У каждого шага — своя проверка:

1. Действие → **verify:** наблюдаемый признак
2. Действие → **verify:** наблюдаемый признак

## Stop conditions
Когда прекратить и спросить пользователя. Здесь живёт предохранитель
(3 попытки), здесь же — красные флаги.

## Output
Точный формат результата: что получает следующий скилл в цепочке.

## References
`ref/harness.md` — читать только если <условие>.
```

Заголовки разделов — **английские и ровно эти шесть, в этом порядке**: линтер
сверяет список буквально. Скиллы пишутся по-английски (§6), русские подписи
выше даны как пояснение.

## 3. Почему такая структура

### Инварианты отделены от процедуры

Это главное решение формата, и оно прямо лечит болезнь gstack.

**Инвариант** — декларативен, живёт вечно, повторяется между скиллами
(«чиним корень, а не симптом»). **Процедура** — императивна, уникальна для скилла.

В gstack они перемешаны: каждый скилл заново пересказывает философию своими
словами. Отсюда 12 000 слов там, где процедуры на 500. Разделив их, мы получаем
механическое правило дедупликации: **инвариант, встретившийся дважды, уезжает
в `core/` и заменяется ссылкой.** Без разделения такое правило неприменимо —
непонятно, что с чем сравнивать.

### У каждого шага своя проверка

Формат `действие → verify:` взят у Карпатого (§4 Goal-Driven). Он делает
невозможным самый частый провал агента — «я сделал 1, 2, 3, наверное работает».
Шаг без наблюдаемого признака завершения не проходит линтер.

### Выход — это контракт, а не пожелание

Раздел «Выход» описывает, что именно получает следующий скилл. Благодаря ему
цепочка `flow/` собирается из контрактов, а не из пересказа: `plan` отдаёт
список задач с критериями приёмки → `build` их принимает → `verify` возвращает
статус → `review` берёт дифф и статус.

Это же даёт проверяемость: контракт можно нарушить, а «сделай хорошо» — нельзя.

### У `ref/` есть условие загрузки, а не просто ссылка

Не «см. чеклист», а «читать `ref/ui-states.md`, **если дифф трогает UI**».
Без условия агент читает всё подряд, и `ref/` превращается в тот же монолит,
только в двух файлах. Матрица 5 состояний — ровно этот случай.

### Стоп-условия — раздел, а не примечание

Предохранители («3 неудачи → откат и вопрос») работают, только если у них есть
фиксированное место, куда агент смотрит. В подвале скилла их не читают.

## 4. Frontmatter: что реально работает

Честно о том, кто какое поле читает:

| поле | кто читает |
|---|---|
| `name`, `description` | **все агенты** |
| `allowed-tools` | только Claude Code |
| `budget`, `tier`, `reads`, `refs` | **никто из агентов** — наш линтер и генератор адаптеров |

Последняя строка важна: не надо обманываться богатым frontmatter. Для Codex,
Kimi и OpenCode это просто текст в начале файла. Поэтому ролевая изоляция
(`role: read-only`) обязана **дублироваться первой строкой тела** — там её
модель хотя бы прочитает.

`allowed-tools` не пишем руками: генератор выводит его из `role`.

## 5. Линтеры

Единственный код в проекте. Всё остальное — markdown.

### `bin/primeskills-lint` — формат

| ID | правило |
|---|---|
| F1 | есть frontmatter с `name`, `description`, `role` |
| F2 | `name` совпадает с именем каталога |
| F3 | `description` ≤ 140 символов |
| F4 | тело ≤ `budget` слов (по умолчанию 800) |
| F5 | ровно 6 разделов, в заданном порядке |
| F6 | каждый нумерованный шаг процедуры содержит `verify:` |
| F7 | у каждого `ref` есть `when` |
| F8 | **дословно скопированный** инвариант в двух скиллах (→ в `core/`) |
| F10 | `role` и `allowed-tools` не противоречат друг другу |
| F11 | каждый `ref` существует, ≤ 700 слов, все вместе ≤ 1 200 |
| F12 | инвариант не пересказывает правило `core/` — либо ссылается на него по номеру |
| F9 | `role` из {`read-only`, `reports`, `exercises`, `write`}: `reports` не трогает работу, но пишет вердикт в `.primeskills/`; `exercises` водит систему под тестом и оставляет в ней данные |
| F15 | у роли `exercises` объявлена `environment` — где именно ей позволено оставлять следы |
| F13 | `tier: flow` имеет `calls`; имена в `calls` и `calls_optional` существуют и не пересекаются; у обычного скилла их нет |
| F14 | frontmatter укладывается в разбираемое подмножество: скаляры, списки в строку `[a, b]`, список плоских отображений (`refs`). Исключение — `hooks`, он проносится нетронутым |
| C1 | всегда загружаемая часть `core/` ≤ 2 300 слов (`CORE_BUDGET` в линтере) |
| C3 | **один вызов скилла ≤ 3 600 слов**: `core/` + все описания + указатель + бюджет самого тяжёлого скилла. Потоки не считаются — они платят за цепочку по замыслу |
| C2 | все три всегда загружаемых файла `core/` на месте |
| C4 | реестр правил `core/` разобрался: есть хотя бы одно `P`-правило и одно `G`-правило |

**F8 ловит дословный повтор**, свёрнутый из целых пунктов списка. Пересказ он
не видит — этим занимается F12.

**F12 закрывает то, что было открытой задачей.** Правила `core/` имеют
идентификаторы (`P1`–`P8`, `G1`–`G17`); линтер собирает их реестр и сравнивает
с каждым инвариантом по значимым словам. Совпало больше трети словаря правила и
номер не назван — ошибка: сослаться, а не переписывать. Пересказ опаснее
копипасты, потому что со временем расходится с оригиналом и начинает ему
противоречить. Проверяется двумя фикстурами: один и тот же текст без ссылки
падает, со ссылкой проходит.

**Бюджет скилла ставится от факта, а не «с запасом».** C3 считает потолок по
объявленному бюджету самого тяжёлого навыка, поэтому резерв, которым никто не
пользуется, съедает потолок так же, как настоящий текст. 2026-08-17 четыре
навыка держали по 800 слов при фактических 405–498 — и ради этой пустоты
приходилось резать живой текст в `core/`. Правило: **факт плюс сотня, округлённая
вверх до полусотни**. Вырос текст — поднимается бюджет, осознанно и с числом.

**C3 — единственное число, которое имеет значение.** C1 и F4 под ним:
поднять `core/` значит отнять у тел скиллов, добавить скилл значит отнять у всех
вызовов сразу (описания постоянны). Размен виден в арифметике, а не в спорах.
Потолок назначен владельцем: 3 000 — 2026-08-17, поднят до 3 600 вместе с
`core/` до 2 100, затем до 2 200 и до 2 300 по факту написанного — 2026-08-18, под разбор трёх внешних ревью. Основание —
правило владельца: результат дешёвого, но плохого скилла обходится дороже, чем
результат хорошего и дорогого. Это всё равно втрое дешевле, чем ≈ 9 000 слов за
один скилл gstack, и вдесятеро дешевле его прохода.

**F14 удерживает подмножество, а не описывает его.** Frontmatter читается
`bin/psmeta.py` — без PyYAML: единственная сторонняя зависимость набора не была
объявлена, и у нового пользователя линтер падал с `ImportError` ещё до первой
проверки. Разборщик моделирует ровно те формы, которые здесь применяются:
скаляры, списки в строку и один список плоских отображений (`refs`). `hooks`
не читает никто в этом репозитории — его парсит сам Claude Code, — поэтому он
хранится как непрозрачный текст. Всё остальное разборщик **отказывается**
читать, а не угадывает: молча неверно прочитанная форма хуже отсутствующей
зависимости, потому что зависимость о себе сообщает. Правило и есть то, что
делает подмножество правдой со временем.

**C4 сторожит сторожа.** 2026-08-18 заголовки принципов стали `## P3.` вместо
`## 3.`, регулярное выражение реестра осталось прежним — и F12 перестал
проверять принципы вовсе, а линтер продолжал печатать «0 problems». Пустой
реестр неотличим от чистого прогона, поэтому теперь он сам является ошибкой.
Тот же день дал второй экземпляр той же ошибки: поднятие потолка C3 сделало
зелёной фикстуру `c3-over`, то есть тихо отключило проверку правила. Правило:
меняешь форму — проверь, что проверка ещё смотрит.

**F11 закрывает дыру в бюджете.** F4 считает только `SKILL.md`, поэтому лишние
инструкции можно было переселить в `ref/` любого размера и остаться зелёным.

### `bin/primeskills-route` — маршрутизация

Берёт таблицу `запрос -> ожидаемый скилл` и ранжирует скиллы по тому, **какую
долю слов запроса покрывает `description`** (со слабым стеммингом: `passing`,
`passed` и `pass` считаются одним словом).

| ID | правило |
|---|---|
| R1 | наверху оказался не тот скилл |
| R2 | нужный скилл выиграл с отрывом меньше 0.15 |
| R3 | таблица ссылается на несуществующий скилл |
| R4 | запрос не делит ни одного слова ни с одним описанием — проверка неприменима, не ошибка |

Ранжирование идёт **внутри яруса**: `tier: flow` во frontmatter отделяет
потоки от скиллов. Причина структурная. Поток называется тем, чего он
достигает, а достигает он того же, что и его звенья, — поэтому у `cycle` и
`build` вокабуляр совпадает неизбежно. Выбор «сделать шаг» или «прогнать
цепочку» — это выбор намерения, и никакая мера пересечения слов его не
различит. Пытаться развести их формулировками значит гнуть описания под
инструмент.

**Как писать запросы в таблице.** Соседние стадии делят пограничный артефакт:
«зелёные тесты» — это выход `cycle` и вход `close` одновременно. Запрос,
называющий границу, двусмыслен по построению. Называйте желаемый исход,
а не текущее состояние.

**Область действия — только английский, и это решение, а не недоделка.**
Описания остаются английскими (`core/OUTPUT.md`, PLAN §8): модель надёжнее
следует английским инструкциям, а отвечает на языке пользователя. Русский
запрос не делит с описаниями ни одного слова, поэтому линтер печатает R4 —
неприменимо. Замер 2026-08-17: из 37 отложенных запросов 32 в этой категории.
Значит R1 и R2 гарантируют одно: **английские формулировки не сталкиваются
между собой**. Про то, попадёт ли модель в нужный скилл с русского запроса,
линтер не говорит ничего и говорить не может.

**Чего он не делает:** не имитирует модель. Это лексическая дымовая проверка:
ярус берётся у ожидаемого ответа, а запросы в таблице написаны словами описаний.
Он ловит одно — два описания, сидящие на одних и тех же словах.

**Настоящая проверка — `tests/routing_model.py`.** Двадцать восемь запросов,
написанных так, как человек в самом деле спрашивает, половина по-русски
(`tests/routing-heldout.txt`), классифицируются независимой моделью по одним
только описаниям.

Цифра, которую стоит держать в голове: на этих запросах **лексический линтер
ошибается в 26 случаях из 28**, а модель — **ни в одном** (28 из 28 при
девятнадцати скиллах, 31 из 31 после добавления тройки выпуска;
`review/routing-model-2026-08-16*.txt`). Инструмент не сломан, он просто отвечает
на другой вопрос: «нет ли двух описаний на одних словах», а не «попадёт ли
живой запрос куда надо». R2 при этом работает как редактор описаний:
провал означает, что в `description` нет слов, которыми пользователь на самом
деле формулирует запрос.

### `tests/run.py`

Прогон: линтер формата на фикстурах, хуки `fence`, маршрутизация на живом
наборе. Двенадцать проверок: на каждое правило есть фикстура, которая его нарушает,
плюс заведомо чистый набор. Прогон — `python3 tests/run.py`, `0 failed`.

## 6. Язык

Скиллы пишем **по-английски**: модели устойчивее следуют англоязычным
инструкциям, а все источники синтеза англоязычны — перевод добавил бы шум
без выигрыша.

В `core/OUTPUT.md` одна строка: **отвечать на языке пользователя**.
Размышление — на любом.

Этот документ и `PLAN.md` — по-русски, они для нас, а не для модели.

## 7. Пример целиком

Скилл `verify`, как он должен выглядеть (400 слов бюджета, здесь сокращённо):

```markdown
---
name: verify
description: Use before claiming work complete, fixed, or passing
budget: 400
tier: pipeline
role: write
refs:
  - path: ref/harness.md
    when: tests touch external services, databases, or spawn processes
---

# Verify

## Trigger
Before any claim of "done", "fixed", or "passing" — and before commit or PR.
Not needed for read-only analysis.

## Invariants
- Absence of a crash is not a pass. See core/GUARDRAILS § Exit-Code Proof.
- Never edit tests, fixtures, or thresholds to make a build green.
- A cycle closes only when the new test passes AND the full suite passes.

## Procedure
1. Run the project's test command → **verify:** exit code is 0
2. Read the runner summary → **verify:** the line reports 0 failed, 0 errors
3. Run the linter/type-checker → **verify:** exit code is 0
4. Confirm the new test actually fails without the fix → **verify:** revert,
   run, observe red; restore, run, observe green
5. Terminate spawned processes, remove temp artifacts → **verify:** none left

## Stop conditions
- 3 failed attempts on the same failure → roll back, report, ask.
- Tempted to change a test to pass → stop. That is the failure, not the test.

## Output
`PASS` or `FAIL` + command, exit code, failing test names.
```

Обратите внимание: этот скилл содержит **три ваших правила**, которых нет ни
в одном источнике — критерий по коду возврата, неприкосновенность харнесса,
закрытие цикла по полному прогону. При этом он укладывается в 400 слов,
тогда как gstack тратит 30 000 на выпуск и не формулирует ни одного из них.
